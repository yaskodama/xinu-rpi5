## 1. Pi 4 にも ELR/SPSR の穴があった —— 同じ起動で A/B を取って実証

Pi 5 で N-Queens の答えが狂った真因（例外エントリが `ELR_EL1`/`SPSR_EL1` を退避しない）が
Pi 4 にもそのまま存在した。ソースでの根拠:

- `irq_dispatch_c` → `proc_preempt()` → `proc_resched()` → **割り込み区間の中で `ctxsw`**
- `irq_entry` は x0–x30 と **q0–q31 まで**退避するのに `ELR_EL1`/`SPSR_EL1` は退避しない
  （リポジトリ全体で `elr_el1` の出現は診断表示のみ）
- その場のコメント自身が「`irq_dispatch_c` は ctxsw を呼びうるので割り込まれた側の FP 状態は
  生き延びねばならない」と書いている。**同じ理屈が ELR/SPSR にも当てはまるのに抜けていた。**

### 計器と切り替え

- `/preempttest?procs=&n=` —— 答えの決まった計算（積・和・剰余のみ。メモリを持たない）を
  複数プロセスで同時に回し、単独実行の基準値と突き合わせる。狂えば原因は文脈切替以外にない。
- `/elrfix?on=0|1` —— 復帰時の書き戻しを実行時に切り替える。**同じ起動のまま A/B が取れる。**

### 計器そのものの検証（これを飛ばすと結論が逆になる）

最初の測定は **mismatch=0**（＝穴が無いように見えた）。しかしそれは
**Pi 4 が先取り(preemption)を既定で切っている**ためで、危険が起こり得ない状態を測っていた。

```
/netpreempt          -> net_preempt=off        （既定）
/rtos-jitter preempt=0 -> pp_calls=1296 off=1296 fired=0   ← 一度も発火していない
/rtos-jitter preempt=1 -> pp_calls=605  off=0    fired=605 ← 発火する
```

`/rtos-jitter` は終了時に `proc_set_preempt(0)` へ戻すので、その後の測定では先取りが
切れている点にも注意（測る直前に必ず `/netpreempt?on=1` を打ち直す）。

### 結果（先取り ON・同じ起動・切り替えただけ）

| プロセス数 | 修正なし `elr_restore_on=0` | 修正あり `=1` |
|---|---|---|
| 2 | `991055 906373` → **mismatch 2/2** | `480003 480003` → **0** |
| 4 | `428433 258890 504716 480003` → **3/4** | 全て 480003 → **0** |
| 8 | 8 個すべて相異なる値 → **8/8** | 全て 480003 → **0** |

期待値 480003。**先取りが入った瞬間に、修正なしでは答えが全部狂う。**
板は落ちなかったので、証明としてはきれいに取れた。

### 退行が無いこと

N-Queens n=13（先取り既定 off）: 1397.2 / 960.8 / 847.8 ms、解 73712、`agree = yes`。
**焼く前と同一。** 修正は既存の経路に影響していない。

## 3. 均一な負荷なら三板とも同じ —— 差は分割の仕方だった

`primes n=300000`（分割の不均等がほぼ無い負荷）:

| コア | Pi 4 | Pi 3 |
|---|---|---|
| 1 | 0.99x | 1.00x |
| 2 | 1.61x | 1.61x |

**速度向上の曲線が完全に一致した。**（Pi 5 も primes は 3.02x。）
したがって N-Queens の差（1.64x 対 2.75x）は**ハードウェアの差ではなく、

## 5. 残っていること

1. **Pi 3 の例外エントリも同じ穴か**を確かめる（Pi 4 と同じ手順が使える）。
2. **Pi 3 の分割方式が Pi 4 の `il=2` と本当に同じか**。同じなら 1.81x 対 2.75x の差が残り、
   別の要因（D-cache の扱い、L2 の共有の仕方）を疑うことになる。
3. **Pi 3 の `/bench` は `kind=fill`/`kind=dining` を受け付けず nqueens(既定 n=12) に落ちる。**

4. 対称SMP型（共有 ready キュー）は Pi 5 にしか無い。Pi 4 への移植は

## 6. Pi 3 に ELR/SPSR の穴は無い —— ARM32 の実装が正しかった

Pi 3 の実機カーネルは **`kernel7.img`＝ARMv7(32bit)** で、`xinu-rpi4`/`xinu-rpi5` とは
別系統（classic Embedded Xinu）である。AArch64 の `ELR_EL1`/`SPSR_EL1` に相当するのは
バンクされた `LR_irq`/`SPSR_irq` で、`system/arch/arm/irq_handler.S` は次のようにしている:

```asm
    sub  lr, lr, #4
    srsdb #ARM_MODE_SYS!        /* SPSR_irq と LR_irq を **SYS スタック** へ積む   */
    cpsid if, #ARM_MODE_SYS     /* SYS モードへ（＝割り込まれたスレッド自身のスタック）*/
    push {r0-r4, r12, lr}
    bl   dispatch               /* この中で clkhandler -> resched() が起こりうる    */
    pop  {r0-r4, r12, lr}
    rfeia sp!                   /* 自分のスタックから PC と CPSR を戻す            */
```

**復帰状態を「割り込まれたスレッド自身のスタック」に積んでいる**ので、`dispatch()` の中で
文脈が切り替わっても各スレッドは自分の復帰状態を持って戻る。`clkhandler.c` は実際に
割り込み中に `resched()` を呼ぶ（58 行目）が、それでも安全である。

**つまり AArch64 版（rpi4/rpi5）は、ARM32 版が正しくやっていたことを再実装の際に
落としていた。** Pi 3 は対象外であり、焼き直しも不要。

# 8. Pi 4 / Pi 3 への移植（2026-09-09 23:xx）

## Pi 4 —— Pi 5 の並列アクター配布をそのまま移植できた

移植前に**前提を検査**した（ここが違えば黙って壊れる）:

- オペコード表が Pi 5 と**完全一致**（0x01–0x48 の全 29 個）
- `VM_MAX_CLASSES` / `VM_MAX_METHODS` / `vm_class` / `vm_str` / `vm_u16` / `VM_MAXF` /
  `code_off` / `code_len` / `n_methods` がすべて存在
- tick ループの形（`while (vm_qh != vm_qt && !vm_frame_done && ++guard < 2000000L)`）が同一

入れたもの（`device/video/avm.c`）:

1. 並列配布の骨格 —— `PAR_NCORES/PAR_SENDQ/PAR_BATCH_MAX`、`code_has_unsafe`（WAIT/描画を含む
   クラスを除外）、`par_send`（コアごとの送信控え）、`par_spawn`（重ならない slot 範囲）、
   `avm_now_us`（`cntpct_el0`/`cntfrq_el0`）
2. 読み込み時の `vm_class_parsafe[]` 判定
3. `avm_dispatch(..., int core)` —— SEND/SPAWN をコアごとの控えへ回す
4. `par_core_hits[]` と `par_dispatch_range`
5. tick ループのバッチ収集 → `smp_parallel_sum(par_dispatch_range, bn, nc)`

`system/tcp_server.c` に `/avm-par`（`on=` / `reset=` / `us= msgs= us_per_msg_x100= core_hits=`）。
Pi 4 に対称SMPスケジューラは無いので `path=workers` 固定。

**build Sep 9 2026 23:10:03**（`compile/kernel8.img`。退行なしのビルド、警告なし）。

## Pi 3 —— 移植ではなく「別モデル」であることが分かった

Pi 3 の AIPL アクターは **Xinu スレッド + メールボックス**である
（`objects[i].tid`（`tid_typ`）、`mb->items = semcreate(0)`、アクターごとの consumer スレッド）。
バイトコード VM（`abcl_vm_load` / `abcl_vm_dispatch`）は**そのスレッド機構の上に載っている**
（VM クラスは `VM_CLASS_BASE=200` 以降の class_id を取り、`dispatch()` の default から回る）。

したがって Pi 4 / Pi 5 のような「メッセージを束ねてコアへ配る」段階が**存在しない**。
Pi 3 は最初から\*\*アクター＝共有 ready キュー上のスレッド\*\*であり、
構造としては対称SMP型に相当する。**バッチ配布の移植は意味を持たない。**

代わりに、三板で比較できる量＝**1 メッセージあたりの実行コスト**を測る計器を入れた:

- `apps/abcl_program.c` —— `abcl_vm_dispatch` を `_inner` に改名して**計時の包み**を被せた
  （早期 return が複数あるので、包まないと漏れる）。`clkcount()` は 1 MHz 自走＝マイクロ秒。
  `smp_core_id()` で `core_hits` も採る。
- `apps/webactor.c` —— `/avm-par`（`reset=1` 対応）。`path=threads` と名乗る。

生成物は `compile/xinu.boot`（`make PLATFORM=arm-rpi3`）。SD の `kernel.img` へ上書きする。

### 焼く前に実機で確かめた（焼き直しを1回節約した）

- **Pi 3 は我々の `.avm` 標本をそのまま受け取れる**。最初 `accepted=0` で拒否されたのは
  **画面の「アクターを受け入れますか」ダイアログ**が無人で答えられないためで、

- `/api/actors` で実行が確認できた（Main 1/1、Worker×4 が各 2/2、Collector 5/5、drops=0）。

### 使えなかった計器（記録として残す）

`/api/loadbal/*`（AIPL レベルの負荷分散器）は魅力的に見えたが、本目的には使えない:

- `busy_ms` / `submitted` / `completed` / `done` はすべて**累積**で、`init` を叩いても戻らない
- 既定の問題が **n=8**（`?n=13` は無視される）で、AIPL 実行でも数 ms しかかからず信号が埋もれる
- `pause?w=` を掛けても `done` が増え続け、ワーカ数を絞れたと確認できなかった

最初の測定では「ワーカ 1/2/4 で makespan 8955/8959/8961 ms」という数字が出たが、
これは**累積値を makespan と誤読しただけ**で、意味を持たない。破棄した。

Pi 3 は `/api/buildtag` が `untagged`、`__DATE__` も埋まっていない。

# 9. 自分の測定の穴を1つ塞いだ（2026-09-09 23:2x）

## 見つけた穴

**AIPL 実験（第 8〜13 節の A/B/C・粒度掃引）は、結果の正しさを一度も外から検証していなかった。**
標本は各ラウンドで合計を照合し、正なら色 2・誤なら色 4 の線を引くが、
**その色は画面にしか出ない**。N-Queens は毎回 `solutions=73712` と `agree=yes` を
突き合わせていたのに、AIPL 側だけこの作法が抜けていた。

## 併せて分かったこと: 標本は 2 ラウンドで止まる

「6 秒の窓で回し続けて平均を取る」という理解も誤っていた。実測では
`AiplP4` は 6 秒窓でも `msgs=8 nbatch=2`、すなわち **2 ラウンドで停止**している
（1 ラウンド 2.9 ms なので、回り続けていれば 2000 ラウンド出るはず）。
`wait(1)` による再起動は一度しか効いていない。

- 測っている量（us/msgs = 1 メッセージあたりの費用）**そのものは有効**。
- ただし**その平均の背後にある標本数は 2 ラウンド分**であって、6 秒分ではない。
  報告書の「6 秒ずつ測る」という書き方は、実態を過大に見せていた。
- `M=32` の標本が `msgs=55 nbatch=2` で止まるのも、
  「AVM のバッチ化が壊れている」のではなく **どの標本も 2 ラウンドで止まる**ことの
  現れだった可能性が高い（第 7 節の記述は要修正）。

最初は「合計が合ったときだけ `wait(1)` を打つ」ように標本を書き換えて、
`msgs` が伸び続けるかどうかで正誤を判定しようとした。しかし
**どの標本も元から 2 ラウンドで止まる**ので、この方法では区別がつかない。破棄した。

## 入れた計器（標本を変えずに済む形）

標本の判定は `line(...,2)`＝正 / `line(...,4)`＝誤 で表されている。
そこで**カーネル側で線の色を数える**ことにした。

- Pi 5 `device/video/avm.c` / Pi 4 同上 / Pi 3 `apps/abcl_program.c` の `case 0x45`（LINE）で
  `col==2` なら `ok++`、`col==4` なら `ng++`
- `/avm-par` に `ok=` / `ng=` を追加（`reset=1` で 0 に戻る）

**判定規則: `ok > 0` かつ `ng == 0` でなければ、その測定値は採用しない。**
標本の書き換えが要らないので、これまでに書いた 39 本すべてにそのまま効く。

## 10.1 Pi 5 / Pi 4 —— 計器は効いた。しかし駆動源が無い

両板で `AiplP4` を 1 本載せて同じ結果:

```
Pi 5  nbatch=2 lastbn=4 us=5724 msgs=8 core_hits=2/2/2/2 ok=1 ng=0 path=workers
Pi 4  nbatch=2 lastbn=4 us=5880 msgs=8 core_hits=2/2/2/2 ok=1 ng=0 path=workers
```

**`ok=1 ng=0`** ―― 検算に通ったラウンドが 1、落ちたラウンドが 0。計器は効いている。
移植した Pi 4 が Pi 5 と同じ `core_hits=2/2/2/2` を出したことで、**移植の正しさも確認できた**。

しかし **`nbatch=2` に対して検算は 1 回**しかない。追ったところ、
**`avm_tick()` を呼ぶ経路が存在しない**。`vmgfx_draw` は WM のウィンドウ描画フックとして
しか登録されておらず、この板は HDMI 無しで `wm_run()` が呼ばれない（実験1で確認済み）。

**したがって AIPL の測定は「読み込み直後に走った 2 バッチ分」しか捉えていない。**
測っている量（1 メッセージあたりの費用）自体は有効だが、
報告書の「6 秒ずつ測る」という記述は実態と違う。**AIPL を継続的に回す駆動源が要る。**

## 10.2 Pi 3 —— 焼く前の照合が甘かった（訂正）

焼く前に「機能の欠落なし」と判断したが、**それは誤りだった**。
比較したのが**文字列の出現回数**だけだったので、次を見落とした:

- **`/version` が消えた**（このソースツリーには元から無い。
  実機で動いていた旧カーネルは**別系統のビルド**だった）

## 10.4 Pi 3 で AIPL を測った ―― アクター＝スレッドの弱点が出た

`AiplP4`（4 アクター・各 1000 反復）を載せた結果:

```
avm-par cores_online=4 us=183229 msgs=18 us_per_msg_x100=1017938
        core_hits=18/0/0/0 ok=0 ng=0 path=threads
```

1. **`core_hits=18/0/0/0` ―― 18 通すべてが核0 で実行された。**
   Pi 3 のアクターはスレッドだが、**この Xinu はスレッドをコア間に分散しない**。
   `smp_parallel_sum` を明示的に呼ぶ経路（`/bench` など）だけが多コアを使う。
   Pi 4 / Pi 5 が同じ標本で `2/2/2/2` を出すのと**対照的**である。
2. `ok=0 ng=0` ―― Collector の検算行に到達していない（ラウンドが完結していない）。
3. 1 通あたり 10,179 µs。Pi 5 の同標本（4 コアで 715 µs/msg）と直接は比べられないが、
   **核0 だけで走っている**ことが桁の差の主因と考えられる。

## 10.5 Pi 3 が固まった ―― これ自体が結果である

`AiplP8`（8 アクター）を載せた直後から **HTTP がまったく応答しなくなった**
（`ping` は 100% 通るのでネットワークは生存）。電源再投入が必要。

Pi 3 では **1 アクター = 1 スレッド**なので、計算の重いアクターを 8 個載せると
Web サーバのスレッドが走れなくなる。Pi 4 / Pi 5 の**アクター＝データ**方式では、
VM は協調的に tick するのでこの問題が起きない。

**これは方式の差が可用性に出た例であり、本研究の主張を補強する材料になる。**
ワーカーズ型（郵便箱・静的分割）を推す理由は速度だけではない ――
**寿命の短い仕事に OS スレッドを割り当てない**という設計が、系全体の応答性を守っている。

# 11. 駆動源を入れて、初めて AIPL を「十分な標本数で」測った（2026-09-10 06:3x）

## 11.1 標本が 2 ラウンドで止まっていた真因

`/avm-run?ms=2000` を最初に入れたとき、**`ticks=7,457,725` も回ったのに
`msgs` も `ok` も 1 つも動かなかった**。追った結果:

- `Main.tick` は**読み込み時に一度だけ**積まれる（`vm_enqueue(-1, id, "tick", 0, 0)`）
- **`WAIT`(0x07) は「フレームの区切り」を立てるだけで、tick を積み直さない**

つまり待ち行列が尽きればそこで終わりで、`avm_tick()` をいくら呼んでも空回りする。
**これが「標本が 2 ラウンドで止まる」の正体**だった。第 7 節で
「AVM のバッチ化が 32 アクターで破綻している」と書いたのは**誤り**で、
どの標本も 2 ラウンドで止まっていただけである。訂正する。

駆動源を「待ち行列が空なら tick を積み直す」形に直したところ、
Pi 4 で `rounds=199 ok=200 ng=0` と、**2 秒で 200 ラウンド**回るようになった。

## 11.2 計器自体の検証（Pi 3 の us は使えない）

Pi 3 の `us` は **2 秒の窓に対して 21,427,509 µs = 21.4 秒**を計上した。10 倍以上である。
原因は明らかで、Pi 3 はアクター＝スレッドなので**複数のディスパッチが同時に計時中**になり、
壁時計の区間が重なって積算される。**Pi 3 の `us_per_msg` は 1 メッセージあたりの費用ではない。
Pi 4 / Pi 5 の値と比べてはいけない。**

Pi 4 の `us` は窓 2000 ms に対し 1,623,818 µs（窓以内）。VM が協調的に回るので重なりが無く、
**Pi 4 / Pi 5 の `us` は有効**である。

重なりの影響を受けない量として、**検算に通ったラウンド数 `ok`** を三板共通の物差しにする。

## 11.3 三板の比較 —— 1 コア性能が揃った 2 枚での対照

**Pi 4(A72) と Pi 3(A53) は N-Queens n=13 の 1 コアが 1401.3 ms 対 1426.5 ms、
差は 1.8% しかない。** つまり素の計算速度はほぼ同じで、
以下の差は**アクターの実行方式の差**である。

2 秒の窓、`ng=0`（全ラウンド検算に通過）:

| 標本 | アクター数 | 1ラウンドの反復 | Pi4 round/s | Pi3 round/s | Pi4 反復/s | Pi3 反復/s | 比 |
|---|---|---|---|---|---|---|---|
| AiplP2 | 2 | 2,000 | 114.5 | 5.0 | 229,000 | 10,000 | 23x |
| AiplP4 | 4 | 4,000 | 100.5 | 8.0 | 402,000 | 32,000 | 13x |
| AiplP8 | 8 | 8,000 | 56.0 | 0.5 | 448,000 | 4,000 | 112x |
| AiplP16 | 16 | 16,000 | 29.5 | 0.0 | 472,000 | 0 | — |

コア別の内訳（`core_hits`）が方式の差をそのまま映している:

| 標本 | Pi 4（アクター＝データ） | Pi 3（アクター＝スレッド） |
|---|---|---|
| AiplP2 | **230/230/0/0** | 114/**0/0/0** |
| AiplP4 | 202/202/202/202 | 207/**0/0/0** |
| AiplP8 | 226/226/226/226 | 167/**0/0/0** |
| AiplP16 | 240/240/240/240 | 197/**0/0/0** |

- **Pi 3 は 1 通も他のコアへ行かない。** アクターはスレッドだが、この Xinu は
  スレッドをコア間に分散しない。多コアを使うのは `smp_parallel_sum` を明示的に呼ぶ
  経路（`/bench`）だけである。
- Pi 4 は 4 アクター以上で 4 コアに均等に散る。**AiplP2 が 2 コアしか使わない**のは
  Pi 5 の実験2（バッチ長がコア数に満たないと残りのコアは 1 通も実行しない）の
  **別アーキテクチャでの再現**である。
- Pi 4 の実効スループットはアクターを増やすほど伸びて飽和する
  （229k → 402k → 448k → 472k 反復/s）。

## 11.4 公平を期すための断り

Pi 3 の駆動源は、前ラウンドの完了を待たずに `sleep(1)` ごとに tick を投入する
（Pi 4 / Pi 5 は「待ち行列が空なら」なので自然に 1 ラウンドずつになる）。
そのためアクターが多いほどメールボックスが詰まり、**Pi 3 の round/s は下振れしている**。
`AiplP8` が `AiplP4` より遅い（0.5 対 8.0 round/s）のはこの影響が大きい。

**下振れの影響を受けない結論は次の 2 つで、こちらは確実である:**

1. **Pi 3 は AIPL のメッセージを 1 通も他コアへ配らない**（`core_hits` は常に `N/0/0/0`）。
   これは投入の速さと無関係な構造的事実である。
2. **Pi 3 は計算の重いアクターを載せると系が止まる**。VM アクターの優先度が
   `default: INITPRIO(20)` で **Web サーバ（同じく INITPRIO）と同値**だったため、
   `AiplP8` で HTTP がまったく応答しなくなった（`ping` は 100% 通る）。
   VM アクターだけ `INITPRIO-5` に下げて解消した。
   **Pi 4 / Pi 5 の「アクター＝データ」方式では、VM が協調的に tick するので
   優先度の設計を間違えても系は止まらない。**

これは本研究の主張を速度以外の面から補強する。ワーカーズ型（郵便箱・静的分割）を
推す理由は、**寿命の短い仕事に OS スレッドを割り当てない**という設計が
系全体の応答性を守ることにもある。
