| | 4コアでの時間 | 直列 656 ms からの速度向上 |
|---|---|---|
| ワーカーズ型（静的分割） | **352.7 ms** | **1.86x** |

**この仕事ではワーカーズ型が 1.58 倍速い。** ただし理由は「静的分割が優れているから」
ではなく、**対称側が核0を使えていない**ことが大きい:

- `ran_per_core` の先頭が常に **0** ＝ 核0 は 1 本もタスクを走らせていない。
  `smpsched_nqueens` の `while (sm_done < ntasks) proc_resched();` で回っている間に、
  空き待ちの二次コア 3 台が先に ready キューから取ってしまう。**実質 3 コア**で解いている。
- 対称側の**タスク数を増やすほど速くなる**（643 → 572 → 558）のは、設計が狙ったとおり
  「偏りが走行中に均される」効果が出ている証拠。ただし核0 を丸ごと失う損の方が大きい。
- 核0 が参加できれば単純計算で 558 × 3/4 ≒ 419 ms。それでもワーカーズ型 353 ms には届かない
  （プロセス生成・文脈切替・ロックの分）。

負荷の性質による差（ワーカーズ型・4コア・5回の中央値）:

| 負荷 | 直列 | 並列 | 速度向上 |

| nqueens n=13（木の大きさが不揃い） | 660.3 ms | 407.7 ms | 1.62x |

## 見つかった不具合

1. **2 方式は同居できない**（設計の主張と食い違う）。対称モードに切り替えたあと
   郵便箱側 `/bench?kind=nqueens&n=13&cores=4` を叩くと:

   ```
   1-core us = 716561   N-core us = 81890460   speedup x100 = 0   agree = NO
   ```

   **82 秒**かかり、しかも**直列と並列で解が一致しない**。二次コアが
   `smpsched_core_loop` の空きキュー待ち `wfe` に居るあいだ郵便箱の仕事を取り落とし、
   核0 が `SMP_WAIT_LIMIT` の肩代わり経路へ落ち、そこへ遅れて起きたワーカが同じ範囲を
   二重に足している、と読める。`smp_worker_poll_once` を core loop に置くだけでは足りない。
2. **対称モードでは重い実行中に板がネットワークごと無応答になる**（数十秒）。
   核0 は `proc_resched` を IRQ 禁止で回すため。実行が終われば戻る。

## 直したもの（この測定を可能にするために）

- **スピンロックをパン屋（原子命令なし）へ**。この板は D-cache OFF で走っており、
  非キャッシュ可能メモリでの `ldaxr`/`stxr` は保証されない。排他版のカーネルは
  実機で「Xinu の画面が出てから halt」した。`make pi5 SPIN=bakery` が既定（`SPIN=exclusive` で旧版）。
- **対称スケジューラを起動経路から外した**。二次コアは起動時ワーカ郵便箱に入り、
  `/smpmode?on=1` のときだけ共有 ready キューへ移る。これで**壊れていても板は上がる**。

## 再現手順

```bash
python3 bench/ab_run.py --host 192.168.3.101 --n 13 --reps 5           # A 側（切り替え前）
curl http://192.168.3.101/smplock?n=20000                              # ロックの自己診断
curl http://192.168.3.101/smpmode?on=1                                 # 対称へ（一方通行）
for t in 4 8 13; do curl "http://192.168.3.101/smpsched?n=13&tasks=$t"; sleep 5; done
```

## 次にやるなら

1. **核0 を対称スケジューラに参加させる**（`smpsched_nqueens` の待ちループで
   自分も ready キューから取る）。これが入って初めて 4 コア対 4 コアの比較になる。
2. **2 方式の同居を直すか、捨てるか**を決める。同居させるなら、郵便箱の仕事を
   ready キューの一種として扱う（idle プロセスがポーリングするのではなく、
   仕事到着でプロセスを起こす）のが素直。
3. 対称モードで**核0 の IRQ を切らずに待つ**（板が無応答にならないようにする）。

## 分かったこと（前回の推測は外れていた）

前回は「核0 が ready キューの取り合いに負けている」と考えたが、**計器はそう言っていない**。

- `loops=0/49993/0/0` `picks=0/1/0/0` ―― 待ちループを回しているのも、`proc_resched` が
  仕事を取れているのも **二次コア**。核0 の欄はどちらも 0。
- `mode=1` で「駆動側が自分の持ち分を直接走らせる」ようにしても、その 1 本は
  **核0 ではなく二次コアに計上される**（`ran_per_core` の先頭は 0 のまま）。

つまり **HTTP 要求を処理しているプロセス自体が、対称モードでは核0 に居ない**。
対称スケジューラに入った時点で、そのプロセスは共有 ready キュー経由で二次コアに拾われ、
以降は二次コアの上で動く。**核0 は系のコンテキスト（NULLPROC/シェル）に留まり、
共有 ready キューを一度も引かない。** だから常に「実質 3 コア」になる。

「核0 が仕事を取らない」のではなく、**核0 はそもそもこのスケジューラに参加していない**。
直すなら、核0 も暇なときに `smpsched_core_loop` と同じことをする（＝核0 の idle を
スケジューラに入れる）必要がある。今回の `mode=1` はそこには届かない。

## 同じコア数で比べる

| | 実際に働くコア | 時間 | 速度向上 |
|---|---|---|---|
| ワーカーズ型 2 コア | 2 | 445.9 ms | 1.52x |
| ワーカーズ型 3 コア | 3 | 378.9 ms | 1.78x |
| ワーカーズ型 4 コア | 4 | **363.8 ms** | **1.86x** |
| 対称SMP型 最良（mode=1, tasks=2） | 3（うち実働は 2 本ぶん） | 474 ms | 1.43x |
| 対称SMP型（mode=1, tasks=10） | 3 | 521 ms | 1.30x |

**対称SMP型の最良（474 ms）は、ワーカーズ型を 2 コアに絞ったとき（446 ms）より遅い。**
核0 の不参加に加えて、プロセス生成・文脈切替・ロック往復・駆動側が resched を
回し続ける分のオーバーヘッドが乗っている。

`mode=1` の効果は明確で、tasks=2 で 748→474 ms、tasks=8 で 591→546 ms。
「駆動側が待つだけでなく自分も計算する」だけで 8〜37% 縮む。

## 未解決の不具合（この版で入れた回帰）

**切り替え前**（二次コアが郵便箱側に居る状態）で `/smpsched` を叩くと、
**解が狂う**: `mode=1` で 98996、`mode=0` で 121391（正解 73712）。
16:02 版では同じ条件で 73712 だったので、17:24 版で入れた回帰。
切り替え後は `mode` によらず常に正解なので、**「参加コアが 0 のときだけ壊れる」**
経路がある。次の起動で最初に確かめること（`tasks` を変えて再現条件を絞る）。
なお切り替え前の `/smpsched` は本来の運用形態ではない（対称スケジューラに誰も居ない）。

## 実験2: バッチ長 —— 並列は core_hits で直接示せた

`AiplP2` の `core_hits=2/2/0/0` が決定的である。**バッチ長がコア数に満たないと、

## 実験1: 核0 の参加 —— 原因は 2 段構えだった

1. **hook が死んでいた**。核0 参加の hook を `wm_run()` の描画ループに置いていたが、
   この板は HDMI 無しで `kernel_main` は `shell_main()` へ落ちるため、
   **`wm_run()` は一度も呼ばれない**（`grep` で呼び出し元が無いことを確認）。
2. **移した先も回らなかった**。核0 の暇は `uart_getc()` の RX 空回りだと考えて
   そこへ移したが、シリアルアダプタが TX→RX ループバックなので RX FIFO が
   ほとんど空にならず、`poll_calls` は HTTP 要求あたり約 1 回しか増えない。
   **`poll_hits=0`**、`ran_per_core` の先頭も 0 のまま。
3. **AIPL 経路では、そもそも核0 は最初から働いていた**。`core_hits` の先頭が
   常に非 0 なのは、`smpsched_parallel` の「呼び手が最後の 1 単位を直接走らせる」
   ぶんが核0 で実行されているから（AVM の tick が核0 で回る）。
   **核0 不参加は `/smpsched`（N-Queens 駆動部）に固有の穴**であって、
   AIPL の配布経路の穴ではない ―― これは前回までの記述の訂正である。

次版（build 21:37:48）では `proc_preempt()` に移した。ここは 100 Hz のタイマ IRQ から
EOI 後に必ず呼ばれ、しかも既存の `if (!IS_IDLE(currpid))` こそが
「核0 は idle だから何もしない」＝不参加の原因そのものだった。

| B2 | 16 | **166.8** | 152.3 | 134.6 | **1.239** |

**予測どおりに分かれた。**
- **散らばっていれば、細かく割るだけでワーカーズ型は追いつく**（1.21 → 1.07 倍差）。
- **固まっていれば、細かく割るほど悪くなる**（1.21 → 1.24 倍差、絶対値も 144.8 → 166.8 ms）。
  郵便箱は区間を**連続**に 4 等分するので、重い仕事が隣り合っていると分割数を増やしても
  同じコアに集まり続ける。

処方は「共有 ready キューへ移れ」ではなく、**多めに分割し、重い仕事を隣り合わせにするな**。
これは郵便箱方式を保ったまま実行できる。

### M=32 は測れない（処理系の限界）

`AiplB1M32` / `AiplB2M32` / `AiplP32` はいずれも `msgs=55 nbatch=2` で**止まる**
（窓を 6 秒→20 秒にしても同じ値）。1 論理ラウンド = 32 通のはずが 32+23 で打ち切られ、
Collector が `got == 32` に届かず次ラウンドを起こさない。`VM_Q=512` なので
キュー溢れではない。**AVM のバッチ化が 32 アクターのこの形で破綻している**。
スケジューリングの結果ではないので実験Bからは除外し、別件として残す。

## 実験C: 4 コアで 4 倍は出ない（仕事は完全に等量）

`core_hits` で「バッチ長がコア数に満たないと残りのコアは 1 通も実行しない」ことが
分かっているので、**1 通 32000 反復に揃えたまま**バッチ長で使用コア数を変える。

| 使用コア | makespan | 1 反復あたり | 2 コア比の実効スループット | 理想 |
|---|---|---|---|---|
| 2 | 69.2 ms | 2.163 µs | 1.00x | 1.00x |
| 3 | 77.7 ms | 2.428 µs | 1.34x | 1.50x |
| 4 | 87.4 ms | **2.731 µs** | **1.58x** | 2.00x |

**分割の不均等はゼロなのに、コアを増やすと 1 反復の所要が伸びる**（2→4 コアで +26%）。
この板は **D-cache OFF** で走っているので、全てのメモリ参照がバスに出る。
1 コア増やすごとに約 +13%。ここから 1 コア相当は約 1.88 µs/反復と外挿でき、
4 コアの実効速度向上は約 **2.75x** ―― N-Queens の 2.21x 頭打ちの主要部分がこれで説明できる
（残りは静的分割の不均等）。

### 未解決: AiplSolo の汚染

1 コア基準値のつもりで作った `AiplSolo`（4 通のうち 1 通だけ 32000 反復、他は 100）は
**85.1 ms = 2.659 µs/反復**で、4 コア全開（2.731）とほぼ同じだった。1 コアしか計算して
いないのに速くならない。有力な疑いは、`smpsched_parallel` の
`while (sp_done < nproc) proc_resched();` という**駆動側の空回り**が共有ロックを叩き続け、
計算中のコアの足を引くこと。次の起動で (a) ワーカーズ型でも同じか、(b) 空回りを
やめた版で消えるか、を確かめる。**上表の 1 コア外挿はこの汚染を避けて 2〜4 コアの
傾きから取った**もので、AiplSolo の値は使っていない。

# 実験A/B/C の取り直しと、**対称SMP型 AIPL 経路の破綻**（2026-09-10 06:4x）

kernel build **Sep 10 2026 06:29:44**。駆動源 `/avm-run?ms=` と検算計器 `ok=`/`ng=` を入れた版。

## 1. これまでの AIPL 測定には 2 つの穴があった

**(a) 駆動源が無かった。** `Main.tick` は読み込み時に一度だけ積まれ、
`WAIT` は tick を積み直さない。したがって `avm_tick` を呼ぶ経路の無いこの板では
**読み込み直後の 2 ラウンドしか走っていなかった**。
（第7節で「AVM のバッチ化が 32 アクターで破綻」と書いたのは誤り。訂正する。）

**(b) その 2 ラウンドは冷間始動の過渡だった。** 暖機してから測ると値が約 2 倍になる:

| 測り方 | AiplSpread1 の 1 バッチ |
|---|---|
| 載せた直後の 2 バッチ（旧方式） | 93.1 ms |
| 5 バッチ | 148.9 ms |
| 19 バッチ | 177.1 ms |
| **暖機後の定常値（窓 2000ms / 4000ms）** | **186.1 / 186.0 ms** |

定常値は窓を変えても 0.05% 以内で一致する。`/bench`(N-Queens) では最初から
暖機を捨てていたのに、**AIPL 側だけこの作法が抜けていた**。
過渡が定常のちょうど半分になる理由は特定できていない（未解決）。
描画リストの蓄積を疑って `cls()` を入れた標本で試したが、差は出なかった（仮説は外れ）。

## 2. ワーカーズ型・定常値（すべて `ng=0`）

### 実験A: ばらつき掃引（総仕事量 128000 反復固定）

| 比 | ms/batch | Spread1 比 | 予測比(静的 makespan) |
|---|---|---|---|
| 1 | 186.0 | 1.00 | 1.00 |
| 2 | 248.1 | 1.33 | 1.32 |
| 4 | 308.7 | 1.66 | 1.65 |
| 8 | 365.1 | 1.96 | 1.98 |
| 16 | 415.7 | 2.23 | 2.28 |
| 32 | 460.1 | 2.47 | 2.57 |
| 64 | 498.8 | 2.68 | 2.81 |
| 128 | 534.3 | **2.87** | **3.01** |

**静的分割のモデルは定常値でも成り立つ**（最遠点で 4.6% 差）。

### 実験B: 分割の粗さ

| 形 | M=4 | M=8 | M=16 |
|---|---|---|---|
| B1 散らす | 301.5 ms | 255.5 ms | **235.3 ms**（改善） |
| B2 固める | 301.5 ms | 322.6 ms | **349.4 ms**（悪化） |

**以前と同じ結論が、正しい標本数で再現した。**

### 実験C: 使用コア数（仕事は完全に等量・32000 反復/通）

| 使用コア | ms/batch | 1 反復あたり | core_hits |
|---|---|---|---|
| 2 | 145.3 | 4.54 µs | 21/21/0/0 |
| 3 | 164.1 | 5.13 µs | 19/19/19/0 |
| 4 | 185.5 | **5.80 µs** | 17/17/17/17 |

2→4 コアで 1 反復が **+27.8%**（旧測定の +26% と一致）。
4 コアの実効スループットは 2 コア比 1.57 倍（理想 2.00）。**この結論は変わらない。**

`AiplUneven`（不揃い）は 1065.5 ms/batch。

## 3. **対称SMP型の AIPL 経路は壊れている**

`/smpmode?on=1` のあと同じ一式を測ると、**検算に落ちるラウンドが出る**:

```
AiplSpread1    ok=37  ng=28   core_hits=178/128/126/128
AiplSpread4    ok=2   ng=78   core_hits=219/186/116/115
AiplSpread32   ok=0   ng=8    core_hits=215/225/122/124
AiplSpread2    ok=0   ng=0    nbatch=1   1 バッチに 6190 ms
```

3 回繰り返すと挙動が回ごとに変わる:

| 回 | AiplP4 | AiplP8 | AiplEq4 |
|---|---|---|---|
| 1 | ok=1 nbatch=1 | ok=157（11.7 ms/batch） | ok=0 nbatch=0 |
| 2 | ok=257（6.3 ms/batch） | ok=144（12.9） | ok=0、1 バッチに 4141 ms |
| 3 | ok=0 nbatch=0 | ok=147（12.9） | ok=0、1 バッチに 4149 ms |

- **正しく速く走る回もある**（AiplP4 の 6.3 ms/batch はワーカーズ型の期待値どおり）
- **まったく進まない回もある**（ok=0, nbatch=0）
- **1 バッチに 4 秒かかる回もある**（ワーカーズ型 185 ms の 22 倍）
- **`core_hits` が不均等**（178/128/126/128）＝ 配り分けが崩れている

**N-Queens の対称経路（`/smpsched`）は正しいまま**である
（`solutions=73712`, `ran_per_core=1/1/1/1`, 411 ms）。
壊れているのは **AIPL のバッチを `smpsched_parallel` で配る経路に固有**である。

### 有力な仮説（未証明）

`smpsched_parallel` は各単位に `fn(lo, hi, smp_core_id())` を渡す。
`par_send` / `par_spawn` はこの `core` でコアごとの控えを選ぶので、
**同じコア番号を持つ実行が 2 つ同時に存在してはいけない**。
郵便箱方式（`smp_parallel_sum`）は 1 コア 1 単位に固定するので起こり得ない。
しかし対称方式では単位は普通の Xinu プロセスであり、**先取りで同じコアに
別の単位が載る**ことがある。そのとき `par_q[core]` と `par_spawn_next[core]` に
書き手が 2 つできる。実験1（核0 を `proc_preempt` から参加させる）で
先取り経路を通したことが、この競合を**顕在化させた**可能性がある。

## 4. 撤回する主張

**「不揃いな仕事では対称SMP型が 1.25 倍速い」（旧・第9節/実験3）は撤回する。**
根拠は次の 2 点である:

1. その測定は**冷間始動の 2 ラウンド分**で、定常値ではなかった。
2. その測定は**正誤を確認していなかった**。いま確認すると、
   対称SMP型の AIPL 経路は**誤った答えを返す回がある**。

**計算が誤っているなら、速さに意味は無い。**
対称SMP型が有利になりうる領域があるという理論的な指摘（静的分割は
最も重い区間に律速される）は依然として正しいが、
**この実装でそれを実測できたとは言えない。**

対称SMP型と AIPL の比較をやり直すには、まず上記の競合を直す必要がある。

## 5. 単位番号への変更は効かなかった（仮説は外れ）

kernel build **Sep 10 2026 07:07:24**。`smpsched_parallel` が配布関数へ渡す第3引数を
`smp_core_id()` から**単位番号**に変え、`par_q`/`par_spawn` の控えが
同時に 2 人の書き手を持ち得ないようにした。計器 `core_hits` は実コアで別に採る。

**ワーカーズ型は不変**（郵便箱経路では単位番号＝コア番号なので当然）:

| 標本 | 修正前 | 修正後 |
|---|---|---|
| AiplSpread1 | 186.0 ms | 182.4 ms |
| AiplSpread16 | 415.7 ms | 403.3 ms |
| AiplSpread128 | 534.3 ms | 527.5 ms |
| AiplEq4 | 185.5 ms | 183.8 ms |
| AiplUneven | 1065.5 ms | 1052.8 ms |

**対称SMP型は直らなかった。** 同じ標本を 3 回:

| 回 | AiplSpread1 | AiplSpread16 | AiplEq4 |
|---|---|---|---|
| 1 | ok=0 ng=0、1 バッチに 6162 ms | ok=1 ng=0、`core_hits=493/0/0/0` | ok=0、1 バッチに 6145 ms |
| 2 | ok=0 **ng=62**、`core_hits=309/67/66/66` | ok=0、1 バッチに 6321 ms | ok=0、6149 ms |
| 3 | ok=0 ng=0 nbatch=0 | ok=0 **ng=16** | ok=0、6161 ms |

**仮説（控えの添字の競合）は誤りだった。** 直っていない。

### 読み取れること（部分的な診断）

1. **1 バッチが 6.1 秒**＝暖機と測定の窓をまるごと 1 バッチが食っている。
   `smpsched_parallel` の `while (sp_done < nproc) proc_resched();` が
   永久に待っている、すなわち**生成した単位が完了しない**。
2. そのあと `core_hits=493/0/0/0` のように**全部が核0** で走る回がある。
   `smpsched_parallel` の先頭にある再入よけ `if (sp_busy) return fn(0, n, 0);` が
   効きっぱなしになっている（＝ハングした呼び出しが `sp_busy=1` を残したまま
   戻ってこないので、以後の呼び出しは全部直列に落ちる）と読める。
   最初のハングの原因そのものは未解明である。
3. **N-Queens の対称経路は正しいまま**（`/smpsched?n=13&tasks=4` →
   `solutions=73712 ran_per_core=1/1/1/1 ms=411`）。
   壊れているのは **AIPL のバッチ配布に固有**である。

### 現時点の結論

**対称SMP型は AIPL のアクター・バッチを正しく配れない。**
N-Queens のように「独立した重い区間を一度だけ配る」用途では動くが、
AIPL のように**短いバッチを毎ラウンド何百回も配る**用途では、
ハングと誤答が混ざる。原因は再入・入れ子の扱いにあると見ているが、
特定には計器の追加と焼き直しが複数回必要である。

したがって本報告では、**ワーカーズ型の測定は完結している**一方、
**対称SMP型との AIPL 比較は「実装が正しく動かないため測定できなかった」**
と書くのが事実に即している。

## 対称SMP型 AIPL 経路の診断（未完）

3 つの仮説を立てて実装・実測し、**2 つは外れ、3 つ目で原因に届いた**。

| 仮説 | 実装 | 結果 |
|---|---|---|
| 控えの添字がコア番号で衝突する | 単位番号に変更 | **外れ**（直らず） |
| 静的スタックを退出中に再利用している | 世代化（4 世代） | **部分的に当たり**。`ng` が 28〜78 → 0〜1、`core_hits` の偏りも解消。`reuse` が 0 でないことで危険の実在を確認。ただし主因ではない |
| **呼び手が自分で計算している** | 計器で分解 | **当たり**。`inline_us=4,150,086` / `wait_us=1,850` / `pp_inline=399`。**399 × 10.4ms（1ティック）= 4.15 秒**が実測と一致 |

対称モードでは呼び手が普通のプロセスとして共有 ready キューに載るため、
先取りのたびに丸ごと 1 ティックを失う。

これが通れば、撤回した「不揃いな仕事での二方式の比較」を初めて正しく測り直せる。
